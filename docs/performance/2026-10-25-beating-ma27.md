**Date:** 2026-10-25
**Before:** `benchmarks/results/optim20/records.jsonl` (see `2026-10-25-optim20-comparison.md`)

smf's **factorization is now faster than MA27's on 19 of 20 cases** (`network_flow` is within 3%). The six cases MA27 still wins are decided by the analyse phase, and on two of them also by the solve phase.

## What changed

### 1. New serial numeric engine (`multifrontal_serial.cpp`, `ldlt_kernel.cpp`)
The old indefinite path built every front from scratch: about 15 heap allocations per supernode, linear `std::find` row lookups, an f×f buffer plus separate L/contribution copies, and a final pass re-copying everything into `FactorKeep`. It also had a quadratic bug: `release_contrib` scanned the whole contribution pool on every call, and the pool grew by one entry per front per factorization, never drained. That alone cost ~30 ms per refactor on `network_flow`.

The new engine, shared by the SPD and indefinite paths:
- a global row→position map for O(1) assembly, and a LIFO stack of packed lower-triangular contribution blocks;
- each front assembled **in place at its final offset in `factor_values`**, so L needs no copy; D is extracted and the pivot block rewritten;
- a dense LDLᵀ kernel with the same MA27-style 1×1/2×2 threshold tests. Small fronts run unblocked with no BLAS calls; fronts ≥ 96 run blocked with a lower-only BLAS-3 update (`cblas_dgemmtr` on MKL). SPD runs the same kernel in no-pivot mode and writes Cholesky-scaled L, so `is_posdef` solves are unchanged;
- a pivot search that scans each column once (top-2 tracking) and skips the off-front scan when the diagonal cannot pass;
- every buffer planned from the symbolic structure and reused, so refactorizations allocate nothing unless delays grow a front.

### 2. Analysis
- **Bug fix:** `clean_lower_csc`'s fast path set `has_diag` from the *last* entry of each column, so clean input almost always took the slow sort/dedup path (573 → 99 µs on `kkt_pde_opt`).
- AMD runs through `amd_2` directly, on a solver-owned reusable workspace (no `amd_order` re-validation, A+Aᵀ rebuild or per-call malloc).
- One double-transpose pass yields the sorted permuted pattern, the value-scatter map and the row form that the etree and column counts share. This replaces a per-column `std::sort`, a binary-search map pass and two internal transposes.
- **Relaxed amalgamation** (`amalgamate_relaxed`): any small child can merge into its parent, not only the one whose columns happen to precede it. Columns are renumbered so merged groups stay contiguous; the order is a topological order of the same etree, so fill is unchanged. Supernode counts dropped 3–5x and most delayed pivots disappeared (`ineq_slack` 103 → 0, `ipm_late` 100 → 0, `pde_opt` 1353 → 836).

### 3. Solve
Extension rows are gathered once per front and multiplied contiguously instead of p·q indirect accesses. The small transposed triangular solve is row-oriented (independent updates instead of a serial FMA chain).

### 4. Build
MSVC now compiles smf with `/arch:AVX2` (cache var `SMF_MSVC_ARCH`, set empty for SSE2), matching the GCC path's `-march=native`. `std::isfinite` (an out-of-line `_dclass` call on MSVC) is replaced in hot loops by a bit test.

### 5. MA27 adapter fix (baseline fairness)
The adapter sized MA27's real array from `INFO(4)` (NIRTOT, an *integer* count). It now uses `INFO(5)`/`INFO(6)` (NRLNEC/NIRNEC) × 5, as IPOPT does, and on IFLAG −3/−4 grows the arrays and refactorizes; retries are timed. MA27 now solves all 20 cases. Its factor-size statistic reports `INFO(9)` (NRLBDU, actual factor storage).

## Where MA27 still wins
All six are analyse-bound:
- **AMD** is 40–50% of smf's analyse on `helmholtz`, `mrf`, `poisson2d`, `network_flow` and `auglag`. MA27's built-in minimum degree plus tree build costs about what AMD alone costs.
- **Per-supernode allocations** in `AnalysisKeep` (`Supernode::children`, `FrontalInfo::row_indices`), several hundred per analyse. These cost tens of µs in a fresh process before the heap warms up, which is what decides `spd_barrier_800` (80 µs vs 27 µs analyse).
- **Solve on amalgamated fronts:** relaxed amalgamation stores explicit zeros (e.g. `network_flow` L is 68K entries vs MA27's 24K), which the solve pays for. Bounding the zero fraction made the factor lose more than the solve gained, so amalgamation is unconstrained for now.

Likely next steps: flat (CSR) storage for supernode children and front rows; a fill-aware amalgamation rule that accounts for solve cost when several solves follow each factorization; porting the task-parallel path (`num_threads > 1`), which still uses the old per-node `FrontResult` code.

## Reproduce
```
cmake --build build --config Release --parallel
python tools/bench/run.py --manifest benchmarks/manifests/optim20.json --output benchmarks/results/optim20_after --trials 10 --warmups 2 --build-dir build
python tools/bench/compare_table.py --input benchmarks/results/optim20_after/records.jsonl --manifest benchmarks/manifests/optim20.json
```
For fast iteration, `build/benchmarks/Release/bench_profile.exe` runs the whole suite in-process (best-of-N per case, smf vs MA27 side by side). With a PDB-enabled build, `--sample analyse|factor|solve --case <id> [--lines]` gives a sampling profile of one phase.

## Verification
- `ctest`: 57/57, including the new `LeanEngine` randomized tests: KKT inertia, random indefinite matrices with zero diagonals across `pivot_u`/`nemin` settings, random SPD, and warm refactorization with zero new allocations. They catch a deliberately broken 2×2 elimination.
- Every benchmark record passes the harness's backward-error gate (`eta_inf` ≤ 1e-10); smf solves 20/20 in all trials.
